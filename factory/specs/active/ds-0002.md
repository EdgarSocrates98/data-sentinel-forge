# Context

§4 of the master plan defines versioned public contracts. Separating public contracts from internal types is required so analyzers and persistence can evolve without breaking consumers (CLI JSON output, future API/MCP).

# Acceptance Criteria

- Pydantic v2 models for all 7 §4 entities: `DiagnosticRequest`, `Evidence`, `Finding`, `DiagnosticReport`, `OptimizationRecommendation`, `ExecutionMetadata`, `CapabilityManifest` — with every field listed in §4.
- Controlled enums: `SourceType`, `AnalysisMode` (economy/balanced/deep/offline per §6), `Severity`, `FindingStatus` (CONFIRMED/PROBABLE/POSSIBLE/UNKNOWN per §2.1), `Platform`, `EvidenceProvenance` (declared/static-inferred/observed per §2.4).
- `schema_version` field on `DiagnosticReport` (contract version constant, e.g. `SCHEMA_VERSION = "1.0.0"`).
- Domain exceptions in `core/exceptions/` with structured error info (code, message, details) — no bare `raise Exception`.
- Stable serialization: `model_dump_json`/`model_validate_json` round-trip preserved in tests; serialized keys stable and documented.
- Public contracts importable from `data_sentinel.core.contracts`; internal types must not leak into that namespace.
- JSON Schemas generated to `schemas/` directory for each public entity (generated by a script in `scripts/` or a test that writes them).
- Unit tests: valid construction, invalid inputs rejected with domain errors, round-trip, schema export, enum value coverage.
- Contract tests: JSON Schema validates a serialized example of each entity.

# Constraints

- No analyzer or persistence logic.
- No speculative fields beyond §4 + serialization metadata (ids, timestamps).
- UTC timestamps, ISO-8601 strings on the wire.

# Review Notes

- Check every §4 field is actually present on each model.
- Finding.status must use the CONFIRMED/PROBABLE/POSSIBLE/UNKNOWN taxonomy — nothing looser.
- Evidence must carry provenance/confidence fields per §4.
