# Grill Gate

- Owner: Edgar (§01.4 enumerates commands and UX requirements).
- Decided at grill: implementer = Devin in-session; review→archive gated by owner acceptance; docs/CLI PT-BR, code/commits English.
- Problem: the CLI is the product's first usable surface — it must wire contracts, config, security, analyzers, and persistence into real commands a user can run offline.
- Out of scope: API server, MCP (Cycle 05), portal, interactive prompts/wizards, cloud connectors.
- Review failure: commands that fake output, non-zero exit on success (or zero on failure), secrets/paths leaked in output, English-only messages where PT-BR required, unhandled tracebacks on bad input.
- Riskiest assumption: exit-code scheme (0 ok / 1 findings-or-user-error / 2 usage / 3 internal — propose and document in ADR) is acceptable.
- Smallest acceptable: all §01.4 commands work end-to-end on fixtures, `--json` everywhere, PT-BR messages, stable exit codes, persisted analyses viewable via `report`.

# Context

Phase 01.4: usable CLI via Typer. Commands: `version`, `doctor`, `capabilities`, `analyze --file/--sql`, `report --input`, `config show`. Requirements: useful --help, PT-BR messages, --json for automation, stable exit codes, optional logs, non-interactive mode, friendly errors. No command without working implementation.

# Acceptance Criteria

- Typer app `data_sentinel.cli:app` exposing exactly: `version`, `doctor`, `capabilities`, `analyze`, `report`, `config show` (config group).
- `analyze --file PATH` runs input through ds-0004 guards → registry-matched analyzer → persists (ds-0007) → prints summary + report path; `--sql` equivalent for SqlStaticAnalyzer. `--profile`, `--json`, `--no-persist`, `--output PATH` options.
- `report --input report.json|report-id` renders a readable PT-BR report (severity, confidence, evidences with locations, recommendations, limitations) — terminal-formatted; `--json` echoes structured report.
- `doctor` checks: Python version, install health, config resolution + sources, store writability, analyzer registry — each line PASS/WARN/FAIL with remediation hints; exit code reflects health.
- `capabilities` emits each registered analyzer's `CapabilityManifest` (from ds-0005 protocol) — JSON-serializable.
- `config show` prints resolved config + sources with secret redaction (ds-0003).
- UX: PT-BR messages, `--json` machine mode on every command, documented exit codes (ADR), `stderr` for errors (not stdout), friendly domain-error rendering (no raw tracebacks unless `--verbose`), non-interactive (no prompts anywhere).
- Integration tests via `typer.testing.CliRunner`: each command happy path + bad input (missing file, traversal attempt, malformed SQL, invalid config), exit codes, --json validity (parses to expected schema keys), PT-BR strings present.

# Constraints

- No unimplemented commands or options (no stubs "coming soon").
- No network calls; offline profile fully functional.
- Don't bypass ds-0004 guards for convenience — CLI args are the allowlist entry point.
- Keep CLI thin: orchestration only, logic stays in domain/analyzer/persistence layers.
