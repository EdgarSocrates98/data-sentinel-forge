# Context

# Acceptance Criteria

- `SqlStaticAnalyzer` implements the ds-0005 analyzer protocol; registered in the registry under `source_type=sql`.
- Explicit `dialect` parameter (`spark` default, `trino`/`presto` for Athena) with dialect-specific notes; same SQL analyzed under two dialects can legitimately differ — test proves dialects are not treated as equivalent.
- Antipattern checks (each documented + severity + rationale + suggestion): `SELECT *` / unbounded projection, CROSS JOIN / JOIN without predicate, non-sargable predicate patterns (function wrapping column in WHERE), `ORDER BY` without `LIMIT`, `UNION` where `UNION ALL` likely intended (flagged as POSSIBLE), `COUNT(DISTINCT)` patterns worth attention, large IN-list literal, implicit (comma) join syntax.
- Reports query shape metadata alongside findings: tables referenced, join count, subquery/CTE counts, top-level clauses — as evidence for downstream Cycle 02 work.
- Parse failure produces a structured limitation (not an exception to the user): states unparseable input, position if available.
- Static-analysis limitation declared in every result: "does not observe physical execution."
- `fixtures/` SQL files per check + valid-clean query + intentionally broken query.
- Tests: each check fires on its fixture, clean query yields no high-severity findings, dialect differences covered, malformed SQL → limitation path, sqlglot version pinned in deps.

# Constraints

- No execution, no EXPLAIN, no catalog lookups.
- Findings status max = POSSIBLE for pattern-based hints (static analysis alone cannot confirm) unless the antipattern is syntactically certain (e.g. CROSS JOIN present → CONFIRMED presence, POSSIBLE impact).
- Keep checks data-driven where practical.
